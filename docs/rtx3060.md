# victory-rtx3060: status on the RTX 3060

Fork of [trustno1-coder/VIctory-NVIDIA](https://github.com/trustno1-coder/VIctory-NVIDIA)
(which comes from avatarmanz/VIctory-7900XTX → fxceless/victory-fork → Marvisak/VIctory),
with the work done on an RTX 3060. No game files are here: use your own copy.

Test machine: Ryzen 5 5600X, RTX 3060 12 GB (driver 621.40), 32 GB of RAM, Windows 11.
All the numbers below come from the run logs; nothing is estimated.

## Measured results

| Base | Mode | Scene | fps | draws/frame |
|---|---|---|---|---|
| fxceless/victory-fork | Series X, scale 1.0 | heavy area | ~6 | ~6,700 |
| fxceless/victory-fork + performance switches | Series X | after warm-up | ~9 | ~3,100 |
| VIctory-NVIDIA (this fork) | Series S, half scale | street, after warm-up | **11.3–11.7** | 2,700–3,300 |
| VIctory-NVIDIA (this fork) | Series S, half scale | heavy area | 3–4 | ~8,000 |
| VIctory-NVIDIA (this fork) | Series S, half scale | **open world** (save loaded), 11/26 15:10–15:27 | **12–14** sustained; peaks of 19–26 in the 5 s averages | — |
| VIctory-NVIDIA (this fork) | Series S, half scale | open world, character standing still, 11/26 15:27 | 11–15 sustained; stretches of **18–21**; peak of **23** seen in the window title | — |

(The 5 s averages are the `victory_gpu::host: N fps` lines of the log; the peak of 23 is the window's
counter, instantaneous.)

In the street (11.7 fps) each frame takes ~85 ms, of which ~68 ms is the CPU preparing
memory (~21 ms of copies, ~38 ms copying back) and almost nothing on the GPU: the CPU is the limit.

### A/B test of 11/26 (scripts/bench-3060.ps1, 3 runs of 6 min, character standing still in the same place)

Average of the last 30 fps lines (5 s each, menus excluded) and per-frame costs from the log:

| Configuration | fps (average / median) | end of run | preparing thread | "copying back" | list translation (CPU) |
|---|---|---|---|---|---|
| as it was (RTX 5070 configuration) | 13.0 / 13.3 | 12–13 fps (77–85 ms) | 70–79 ms | 26–28 ms | ~400 ms |
| `-SixCores` | 12.8 / 13.4 | — | 56–63 ms | — | ~295 ms |
| **`-SixCores -SmallOnCard`** (now the default) | **14.0 / 13.5** | **15–16 fps (61–66 ms)** | **55–58 ms** | **15.6 ms** | **~263 ms** |

- `-SixCores` (fewer helper threads for a 6-core processor) cuts the CPU work, but
  on its own does not change the fps: the thread that prepares submissions is still the limit.
- `-SmallOnCard` (buffers from 64 KiB up compared on the card) drops "copying back" from ~27 to
  ~16 ms per frame. The card is then ~70% busy: it is the next wall, right behind the CPU.
- Scenes vary a little from run to run (~5%), so the difference in average fps is small; the
  drop in CPU times is clear and repeats on every line.

The launcher now turns both on by itself on processors with up to 12 threads; `-Classic` goes back to how it was.

### Round 2 of 11/26 (bench-3060 `-Set 2`, automatic Enter in the menu, same save)

Average of the last 40 fps lines (5 s each); 1% low and P99 from the pacing meter (last 10 s):

| Configuration | average / median fps | end of run | 1% low | P99 | preparing thread | card busy |
|---|---|---|---|---|---|---|
| round 1 default | 13.6 / 14.0 | 12–17 | 7.8 fps | 121 ms | 59 ms | 64% |
| render scale 0.4 (432p) | **15.0 / 15.1** | 14–17 | 8.1 fps | 110 ms | 55 ms | 64% |
| up to 16 submissions joined (was 8) | 14.2 / 14.8 | 15–18 | **9.2 fps** | **103 ms** | 58 ms | 66% |

- Joining up to 16 submissions improves the worst frames (1% low +18%, P99 −15%) at no picture cost:
  it is now the default.
- 432p gives ~10% more average fps, with a softer picture: option `-Resolution 432`.

**Summary: 14–17 fps in the open world after warm-up** (averages of 13.6–15.0 per 6 min run;
1% low of 8–9 fps), on an RTX 3060 with a Ryzen 5 5600X.

### Round 4 of 11/26: a code change that did not win

Hypothesis: of the 11 ms of refreshes per frame on the preparing thread, most would be the serial
check of which copies have nothing new. I put a timer on it and a parallel version
(`VICTORY_FILTER_WIDE`).

| Configuration | average / median fps | preparing thread | refreshes |
|---|---|---|---|
| default (16 submissions joined, 540p) | **15.2 / 15.4** | 55 ms | 10.9 ms |
| + parallel filter | 13.6 / 13.8 | 59 ms | 11.3 ms |
| 432p + parallel filter | 15.4 / 15.5 | 55 ms | 10.7 ms |

The timer showed that the serial check costs only **0.5 ms** per frame: the hypothesis was wrong and the
parallel version was removed. The 11 ms come from one big flush (~7,300 refreshes, once per frame)
that already runs on several threads; there are now timers inside it for the next round. The default reached
15.2 fps on average in this round.

### Round 5 of 11/26: how much runs vary, and where the refreshes go

| Configuration | average / median fps | preparing thread |
|---|---|---|
| default | 13.8 / 14.9 | 58 ms |
| 432p | 14.4 / 15.1 | 58 ms |
| default again | 14.1 / 14.2 | 59 ms |

- **The same configuration gave 13.8, 14.1 and 15.2 fps** (this round and the previous one): differences of ~1 fps are
  noise. From now on each change is also judged by the preparing thread's time (much more stable).
- **The ~11.5 ms of refreshes:** the big flush (~7,300 copies, once per frame) takes ~6 ms from start to
  finish, with the threads adding up ~6 ms checking and ~10.5 ms updating; the rest (~5 ms) is ~41 small
  flushes. It runs on 4 threads (3 reserved + the preparing one): `VICTORY_WIDE_THREADS` now picks
  how many (round 6).
- **The preparing thread, per frame (~58 ms):** list steps 22–24 ms (refreshes ~11.5), copies in
  card memory 8–9, planning steps done on the card 7–8, bytes under shader writes 6–8, write
  watch 5, list submission 2.

## What this fork adds

- **Frame pacing meter** (`crates/victory-gpu/src/pacing.rs`): every 10 s,
  average fps, 1% and 0.1% low, median/P95/P99 frame time, frames over
  100/250/1000 ms, and the total since the start. On by default; `VICTORY_PACING=0` turns it off.
- **Graphics stage watch** (`crates/victory-gpu/src/gfxwatch.rs`): records each stage
  reached (device, first shader, first pipeline, first list, first
  Present, first frame, first draw/dispatch) and warns of a black screen or hang.
- **Shader cache built ahead of time, valid on NVIDIA** (`apps/victory/src/translate.rs`):
  `victory shaders` now honours `VICTORY_HOST_WAVE` and `VICTORY_VIEW_LIMIT`. Before, the cache
  was generated for "no limit" and a run on NVIDIA (32-wide waves, heap of 1,000,000
  views) used none of it. On the 3060: 25,689 shaders in 156 s; the first run no longer
  spends minutes on a black screen with the CPU at 100%.
- **Log of every run to a file** and **frame capture for `victory replay`**
  (`scripts/play-nvidia.ps1 -Capture` + `scripts/capture-now.ps1`).
- **Tuning for 6-core processors** (`play-nvidia.ps1`, default with up to 12 threads): fewer
  helper threads and small buffers compared on the card (see the A/B test above). `-Classic` turns it off.
- **Automatic A/B test** (`scripts/bench-3060.ps1`): three runs in a row, each closed by itself,
  with Enter pressed automatically in the menu (`VICTORY_KEYS`) to continue the save.
- **Up to 16 submissions prepared together** by default (`VICTORY_JOIN_PARTS=16`, `VICTORY_JOIN_LISTS=96`).
- **Performance build** (`[profile.perf]`, `scripts/build-perf.ps1`): full LTO, one
  codegen unit, `-C target-cpu` of the processor.

## How to use

```powershell
copy victory.example.toml victory.toml   # and set game_dir to your copy's folder
cargo build --locked --profile diag -p victory --features diagnostics
$env:VICTORY_HOST_WAVE='32'; $env:VICTORY_VIEW_LIMIT='999999'; $env:VICTORY_BVH_MISS='1'; $env:VICTORY_NAN_SCRUB='1'
target\diag\victory.exe shaders <game-folder>\shaders.rpf     # once per build
scripts\play-nvidia.ps1 -Exe <game-folder>\game_scarlett_master.exe
```

## Known issues (on the 3060)

- **Blown-out light / white haze** in open sunlit scenes (recorded in the heavy area, 4 fps).
  Not diagnosed yet; the next step is to capture such a frame and reproduce it with
  `victory replay`.
- **Character heads/skin** not drawn or transparent on the fxceless base; not yet
  checked on this fork.
- **Ray tracing**: the 7 compute programs refused by the driver ("Shader wants wave lane
  count of 64 but maximum wave lane count for device is 32", D3D12 debug layer)
  belong to the BVH builder (`XboxBvhBuilder.dll`). With `VICTORY_HOST_WAVE=32 VICTORY_WAVE_WHY=1
  victory translate shaders.rpf --warm <list>` they all stay at 64 lanes for the same reason:
  shared LDS in a group of more than 32 threads, with reads and writes in the same stretch where
  only some of the lanes pass (`lds_meetings` in `emit/lower.rs` cannot order it with
  barriers). Also an open question in the original project (Marvisak/VIctory PR 2311). Even
  if solved, turning ray tracing on cost half the fps on the 7900 XTX.
- 5 more shaders do not translate ("a descriptor read only as data is not supported").
